## Contrôles d'accès et persistance
- `app_user_roles` : trois rôles présents (`user`,`admin`,`coach`), une entrée chacun. RLS activé ; lecture de son propre rôle seulement, écriture client révoquée.
- `candidate_profiles` : deux profils ; RLS activé ; politiques propres à l'utilisateur pour lecture/insertion/mise à jour. Les préférences d'onboarding sont persistées par `writeProfile` en upsert sur `user_id`.
- API `/api/interview/[action]` : appelle `auth.getUser`, vérifie rôle `user`, puis transmet au service local ; contrôle du code seulement, pas de validation d'entretien authentifié complète.
- `getAppRole` interprète toute absence de rôle comme `user` ; comportement à évaluer pour comptes créés sans attribution explicite (pas de promotion implicite aux rôles privilégiés).
- La protection de `/interview` côté proxy n'est pas une garantie sur les API ; les contrôles API restent nécessaires.

## Résolution S3-01-A06 — 2026-10-24
- Cause : le script utilisait le rôle comme partie du mot de passe (fichier à trois colonnes). Une deuxième anomalie de synchronisation Playwright/React apparaissait lorsque le formulaire était rempli avant hydratation.
- Correctifs : lecture séparée des colonnes email/password et attente du chargement du login avant saisie.
- Auth Supabase confirmée HTTP 200 pour les trois comptes de démo. Tests authentifiés de navigation, isolation des rôles et déconnexion : PASS user, admin et coach.
- Le chargement de profil est revérifié sur reload, sans modification de données. La persistance après modification sera validée séparément.
- A06 résolue ; aucune réinitialisation de mot de passe ni modification sensible Supabase.
